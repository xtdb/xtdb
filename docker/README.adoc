= Docker

== Building a local image for testing

* Make sure to install docker buildx (`docker-buildx` package in Arch Linux)
* Make sure your Docker daemon is running
* `./scripts/build-standalone-image.sh [--clean]` will build and tag as `xtdb/xtdb:latest`, and load it into your images list.
  The `--clean` flag can be used to ensure the xtdb uberjar is rebuilt.
* To run: `docker run -ti --rm -p 5432:5432 xtdb/xtdb` (this will run the server, exposing port 5432)

== Running other node modes

The image's `ENTRYPOINT` invokes `xtdb.main`, with the container command supplying its arguments (defaulting to `-f config.yaml`).
Override the command to run any other top-level `xtdb.main` command — e.g. a compactor-only or ingest-only node:

[source,bash]
----
docker run -ti --rm -v ./my-config.yaml:/config/xtdb.yaml xtdb/xtdb ingest -f /config/xtdb.yaml
docker run -ti --rm -v ./my-config.yaml:/config/xtdb.yaml xtdb/xtdb compactor -f /config/xtdb.yaml
----

(In Kubernetes, set `args:` on the container to achieve the same.)

== Customizing the local image

If you wish to build the local image with a different default configuration included, you can change the content of the `standalone/local_config.edn` file prior to building, or create a new file and replace references to `local_config.edn` with the new config file.
The created uberjar should have all XTDB modules included, so the node can be configured however you wish.

== Builder image (custom JRE)

The `jlink` stage of `docker/Dockerfile` is pre-built and published as `ghcr.io/xtdb/xtdb-builder:<tag>` so CD doesn't re-run `./gradlew buildCustomJre` on every build (it takes ~5 min on `linux/arm64` under emulation).

The builder content depends only on:

* the JDK base image (`eclipse-temurin:25-jdk-alpine` in `docker/builder.Dockerfile`)
* `build-logic/jlink/` (the jlink module list and gradle wrapper inputs)

=== When to bump it

Any of these is a reason to cut a new builder image:

* `build-logic/jlink/` changes (a module added or removed from the custom JRE).
* We deliberately move to a newer JDK feature release.
* The upstream base image ships a fix we need — most often a CVE in the JDK itself (e.g. a fix landing in a new `eclipse-temurin:25-jdk-alpine` patch tag).
  Check the https://github.com/adoptium/temurin25-binaries/releases[Temurin release notes] (or the CVE advisory) for the patch version that carries the fix, so the tag you bump to is confirmed fixed rather than just newer.

=== Bumping and rebuilding

Pick a new tag, e.g. `YYYYMMDD-N`.

. Run the https://github.com/xtdb/xtdb/actions/workflows/builder.yml[Build xtdb-builder image] action (manually triggered), passing the new tag (e.g. `20261124-2`) as its input, to build and push the image from CI.
. Once it's confirmed pushed, update the `BUILDER_IMAGE` default in `docker/Dockerfile` to match and commit it.

If the fix needs to reach an already-released line as well as `main`, make the same `BUILDER_IMAGE` change on that maintenance branch (see link:../dev/RELEASING.adoc#older-line-patches[patch releases on an older line]) — bumping the builder image doesn't retag or rebuild the XTDB images that `FROM` it on its own.

=== Propagating to published images

The builder image bump only takes effect once something rebuilds `docker/Dockerfile` `FROM` it:

. Run the https://github.com/xtdb/xtdb/actions/workflows/edge.yml[XTDB Edge] action (manually triggered) against `main` (and any maintenance branch you bumped) to push new `edge`-tagged images built on the new builder.
. Sanity-check the published image picked up the fix:
+
[source,bash]
----
docker pull ghcr.io/xtdb/xtdb:edge
docker run --rm --entrypoint java ghcr.io/xtdb/xtdb:edge -version
----
+
and confirm the reported version matches the fixed one.
. A full release still needs the normal link:../dev/RELEASING.adoc[release process] to get the fix onto a versioned tag rather than just `edge`.

== Docker compose setup

There is a docker compose setup under link:docker-compose[docker-compose]. It uses https://github.com/gaul/s3proxy[S3Proxy] for object storage and confluence kafka (with KRaft, so no Zookeper needed). It uses the `xtdb-aws` image but hooks in a tweaked config pointing it at S3Proxy. It should then be as simple as running `docker-compose up` in the `docker-compose` folder. When shutting down or restarting from scratch it is likely useful to run `docker-compose down --volumes --rmi all --remove-orphans` to remove any dangling dependencies.
