== Getting started

XT2 uses https://gradle.org/[Gradle] - a JVM build tool that supports multi-module, polyglot projects.
You do not need to install Gradle to develop XT2 - there is a Gradle https://docs.gradle.org/current/userguide/gradle_wrapper.html[wrapper] in the repo.

* Java classes are (re-)compiled automatically when you (re-)start a REPL or run tests
* Start a REPL with `./gradlew :clojureRepl` (potentially requiring `./gradlew clean :clojureRepl`)
** `-PreplPort=7888` if you need the REPL on a specific port (e.g. for Clojure MCP)
* Once you've connected to the REPL, in the `user` namespace, run:
** `(dev)` to require and go to the `dev` namespace.
** `(go)` to start up the dev node
** `(halt)` to stop it
** `(reset)` to stop it, reload changed namespaces, and restart it
** if you're using Emacs/CIDER, `cider-ns-refresh` will do all this for you - `C-c M-n M-r`, `, s x` in Spacemacs, `, r r` in Doom.
** Conjure users can use `ConjureRefresh`, see the https://github.com/Olical/conjure#mappings[docs] for bindings
** see https://github.com/weavejester/integrant-repl[Integrant REPL] for more details.
* You should now have a running XTDB node under `dev/node` - you can verify this by calling `(xt/status node)` (in the `dev` namespace).
* Most of the time, you shouldn't need to bounce the REPL, but:
** if you add a module, or change any of the dependencies of any of the modules, that'll require a REPL bounce.
** if you change any of the Java classes, that'll require a REPL bounce
** otherwise, `(dev/reset)` (or just `(reset)` if you're already in the `dev` ns) should be sufficient.
** Please don't put any more side-effecting top-level code in dev namespaces - you'll break this reload ability and make me sad.
** Run `git config core.hooksPath .githooks` to add xtdb hooks to your local repo.

== Custom JRE (jlink)

XTDB builds a custom minimal JRE via link:../build-logic/jlink/build.gradle.kts[jlink] to slim down Docker images and local task execution.
All `Test`, `JavaExec`, and `clojureRepl` tasks automatically use this custom JRE.

If you hit missing-module errors (e.g. `ClassNotFoundException` for something in the JDK):

* *Escape hatch:* add `-PfullJdk` to your Gradle command — e.g. `./gradlew :clojureRepl -PfullJdk`
* *Fix forward:* add the missing module to the `jlinkModules` list in `build-logic/jlink/build.gradle.kts` and rebuild.

== XTDB 'playground'

XTDB nodes can be started in 'playground' mode - either through `./gradlew :run`, `clj -m xtdb.main playground` or the standalone Docker image, or by running the `playground-config` `ir/set-prep` in the `dev` namespace.

In playground mode, to begin with, we only start the pgwire server, without an associated XTDB node.
Then, whenever a new connection is initiated, we create a new isolated in-memory node for every distinct 'database' specified in the connection parameters.

This is particularly useful for non-JVM testing - see the `/lang` README for more details.

== Debugging Arrow memory leaks

An Arrow "Memory was leaked" error reports the *close-time detection* stack, not the allocation site.
To get the allocation site, enable Arrow's debug allocator: the leak error then gains an `event log for Allocator(...)` section with `ALLOCATE` stack traces.

`-D` on the command line and `JAVA_TOOL_OPTIONS` won't work - `build.gradle.kts` pins `-Darrow.memory.debug.allocator=false` in `defaultJvmArgs`, which every `Test`/`JavaExec`/`clojureRepl` task inherits, and that overrides anything passed in.
Flip that entry to `=true`, and flip it back before committing: the debug allocator does per-allocation bookkeeping.

Two things worth knowing when hunting one down:

* XTDB leaks are frequently *failure-path cleanup gaps* - a buffer opened and then orphaned because an exception unwinds past its close.
  Look for `openSlice`/`open*` whose result is handed off without a `.use`/`closeOnCatch`, on a path that can now throw.
  `xtdb.util/closeOnCatch` closes on exception only, which is what you want when the success path's consumer already owns the buffer.
* Property-test shrinking is unreliable for leaks - the shrinker assumes a determinism that leaks don't have, so its `:smallest` case can misattribute.
  Bisect with the property test across commits at a high `-Piterations`, then confirm a single-op repro with a plain `deftest` under the debug allocator.

The leaking allocator's name identifies the subsystem - e.g. `leader-log-processor` is tx indexing, not the query allocator.

== General Coding Principles

We aspire to use Clojure-inspired simplicity throughout (even when writing Kotlin).
XTDB is an *essentially* complex codebase (cf. Out of the Tar Pit), so we must wherever possible avoid adding additional accidental complexity on top of that.
This means that we deliberately choose to take longer with code changes in order to do the Right Thing™, rather than the quick thing.

Specifically, this means:

Make illegal states unrepresentable::
+
If your types can only represent valid states, you get correctness by construction instead of by validation (cf. https://blog.janestreet.com/effective-ml-revisited/[Yaron Minsky's principle]).
+
* If two fields are always set together, they belong in a single composite type.
* If a field only makes sense in some contexts, use sealed types to separate those contexts rather than making it nullable everywhere.
* If a value is always the same in a given context, the data structure is wrong for that context — change the structure rather than passing a constant.
+
The corollary: **don't pass hack values.**
If you find yourself passing `true`, `null`, or `emptyMap()` to satisfy a field that doesn't apply, that's a sign the type is complecting two concerns.
+
--
*Worked example* - the Kafka leader transition (#5773, `modules/kafka/src/main/kotlin/xtdb/api/log/KafkaCluster.kt`).
A `Map<TopicPartition, Pending(token, Deferred)>` plus a nullable processor field collapsed into a single sealed `ListenerState` held on `TopicSubscription`: `Following | Transitioning(deferred) | LeaderCommitted(processor)`.
The `Transitioning` instance serves as its own identity token - a superseded transition's completion is dropped by `listenerState !== cmd.transitioning`, with no generation counter anywhere - and the field stays private behind `onTransitionComplete` / `evict` / `await`.

Four smells travel together; spot one and go looking for the other three:

* A `Map<Id, State>` alongside the objects those Ids identify -> put the state *on* the object.
  A side-map is a second source of truth, and it drifts.
* A token/generation/version counter answering "is this still the operation I started?" -> use the object's identity (`a !== b`).
  If you're holding the object, you don't need to number it.
* A field that's null in some states and set in others, guarded at each use -> a sealed hierarchy, one variant per state carrying exactly its valid data, driven by an exhaustive `when` with no `else`.
* Reaching into another object's fields to decide what to do to it -> move the behaviour onto that object; pass the event in and let it extract what it needs.
--

Tidy first::
+
We develop using https://tidyfirst.substack.com/[tidy-first] methodology — separate equivalence changes (refactorings that don't affect runtime behaviour, changes that increase our options) from changes that advance behaviour.
Even on feature branches, a tidying change gets its own commit and is often cherry-picked to `main` independently, so that the resulting PR is easier to review.
See link:GIT.adoc[] for more on how this works in practice.

Intentional defaults::
+
Kotlin parameter defaults are appropriate when the default is the overwhelming norm and only tests or unusual configurations would override it — e.g. HashTrie page sizes, flush timeouts.
+
For data structures where the caller SHOULD care about every field (wire format types, domain records), don't use defaults — force every construction site to be explicit.
Defaults hide intent; a caller can accidentally omit a field and get a value that compiles but doesn't mean what they think.

Name the database, not the `db`::
+
The bare name `db` is reserved for the `Database` object; the database *name* is `db-name` in Clojure, `dbName` in Kotlin.
The two coexist in the same scopes — `scan`/`emitScan` resolves a name into a `Database` — so a bare `db` holding a string misreads.
Concretely, the scan logical-plan option is `:db-name`, and planner pairs are `[db-name table-ref]`.
The user-facing XTQL surface is the exception and keeps its own key: `(from {:db "…", :table …})`.

Import, don't fully-qualify::
+
In Kotlin and in Clojure alike, add the import and use the short name — `IKeyFn$KeyFn/SNAKE_CASE_STRING`, not `xtdb.api.query.IKeyFn$KeyFn/SNAKE_CASE_STRING`.
Nested types need importing in their own right: importing `IKeyFn` does not bring in `IKeyFn$KeyFn`.

One space, never aligned::
+
Don't pad `=` — or `:`, or anything else — with extra spaces so that it lines up with the neighbouring lines; one space each side, always.
Aligned blocks make noisy diffs, because adding or renaming one key forces re-alignment of the whole block and drags unrelated whitespace through the review.
Where the surrounding code is already aligned, don't propagate the style: write new lines single-spaced and leave the neighbours alone.

Visibility follows intent, not the caller count::
+
"The only callers are in-module or in tests" is not grounds for making something `internal` or `private`.
We design public surfaces ahead of their consumers — the granular and batch write APIs on `OpenTx.Table` are deliberately exposed for external-source writers that don't exist yet.
+
Tighten a genuine implementation-detail leak — `OpenTx.Table.txRelation`, the raw staging relation behind those APIs, is `internal` for exactly that reason.
For anything else, ask about the intended surface rather than inferring it from a caller grep.
Visibility is a design decision in the same family as _Make illegal states unrepresentable_ and _Intentional defaults_: the declaration states what callers may do, so it has to be chosen rather than derived from what they happen to do today.

Inject the collaborator; don't reach for a `Factory`::
+
A factory earns its keep only when instances must be created per-something at runtime, by code that doesn't have the dependencies to hand.
`Compactor.Driver.Factory` qualifies — `Compactor.Impl.openForDatabase` creates one driver per database.
`LeaderLogProcessor` doesn't: its driver has a single construction site, `LogProcessor.openLeader`, which already holds `partitionStorage`, `partitionState` and `blockUploader`, so it takes a `LeaderDriver` as a constructor parameter instead.
+
Before writing `interface Factory`, look at every call site of the thing being constructed.
One site that already has the arguments means a plain constructor parameter — and direct injection shrinks the consumer as well, because the collaborator absorbs the parameters the consumer only held in order to pass them along.

Valid time is when a fact becomes true, not what it describes::
+
Valid time models when an assertion becomes true, becomes known, or is reported.
The instant a fact *describes* — a reporting period's start and end, an event's effective date — is an ordinary domain column, and stays one.
+
Back-dating valid-from to the period a fact describes asserts that we held the fact before it existed: an organisation does not report its FY2024 net income at the start of 2024, so a flow figure's valid-from is the date it was filed, not its `period_start`.
An instantaneous measure differs — an as-of balance is true as of its `period_end`.
When choosing valid-from for a CDC or indexer put, ask "when did this become true or known?", not "what date does it refer to?".

=== Comments

Comments that merely restate the code add visual noise without value.
Assume your reader is a senior developer familiar with XTDB and its codebase, Clojure/Kotlin, and the principles in this section.

**Don't write:**

* Comments that repeat the function/variable name
* Docstrings that describe obvious behaviour
* Step-by-step narration of what code does
* Caller lists on a function - "called by X to do Y", "the canonical caller is Z".
  Document the function's own contract: what it does, its threading/locking discipline, its preconditions.
  The contract is stable; the call graph isn't, so a caller list becomes either a lie or a maintenance chore.
  If a *specific* call site needs explaining (unusual sequencing, a workaround), comment at that call site instead.
* "Used to be" narration - "this used to use X", "mirrors the old mutex shape", "previously we did Z".
  A comment that only lands as a contrast with the previous code rots at the next refactor.
  Ask whether it would make sense to a reader with no knowledge of prior versions; if not, move it to the commit body and describe the current contract directly.
* Re-narration of an established pattern at every site it's applied.
  A `close()` that closes things needs no comment, nor a "Phase 2 of teardown" label.
  Document the pattern once in its canonical place (e.g. link:doc/coroutines.adoc[] for two-phase teardown) and leave the instances bare, keeping only the genuinely non-obvious: a stated precondition, a real gotcha (Arrow won't close a parent allocator while a child buffer is live, so the allocator closes last), subtle correctness reasoning.

**Do write:**

* Rationale for counter-intuitive choices ("This is for performance, because...")
* Non-obvious constraints or invariants ("this might be mutated by...", "the obvious solution is X but this doesn't work because Y")
* Gotchas and edge cases ("this can be null if...")
* Links to issues or external context ("see #1234", "per RFC 7231 §6.5.1")
* Warnings about subtle behaviour that could trip up future developers

=== Errors

Use `xtdb.error` (aliased as `err`) for throwing errors — not raw Java exceptions.
We're migrating the codebase to this convention; new code should always use it.

Each error takes a namespaced keyword as its error code (e.g. `::my-error-code`) and a human-readable message.
Choose the appropriate anomaly category:

* `err/incorrect` — bad input or configuration (caller's fault)
* `err/unsupported` — feature not (yet) implemented
* `err/fault` — internal error (our fault)

See `api/src/main/clojure/xtdb/error.clj` for the full set of categories and their semantics.

=== Internal-but-public declarations

Some Kotlin declarations have to stay `public` without being public API — they're called from Clojure over interop, or from another module.
Kotlin `internal` isn't an option for either: it name-mangles the JVM symbol (so Clojure can't resolve it) and it doesn't cross module boundaries.

Mark those with `@InternalApi` (`api/src/main/kotlin/xtdb/InternalApi.kt`), a `@RequiresOptIn(level = ERROR)` marker.
The declaration stays public — Clojure and cross-module callers are untouched — while a Kotlin caller has to write `@OptIn(InternalApi::class)`, at the declaration or as a `@file:` annotation.

`@InternalApi` and `/** @suppress */` are complementary, not alternatives:

* `/** @suppress */` hides the declaration from kdoc, and enforces nothing.
* `@InternalApi` is a compile-time barrier for Kotlin callers, and does not hide anything from kdoc.

So an internal-but-public member carries both.
`grep @InternalApi` enumerates the whole surface; each site SHOULD carry a comment saying what would have to change for it to become genuinely `internal` (see `OpenTx`'s constructor for the shape).

=== Clojure style

Type-hint at the source, not at the call sites::
+
Hint where the value is introduced — the destructuring form, the `let` binding, the fn param — rather than at each `.method` call.
`{:keys [^String default-db]}` fixes every use of `default-db` in scope; `(.databaseOrNull db-cat ^String default-db)` fixes one.

Don't hint speculatively::
+
A *resolved* Java instance-method call already carries its declared return type, and that type flows — into the next call in a chain, and into a `let`/`with-open` binding.
So `(with-open [conn (.connect node db-name)] (.submitTx conn ops opts))` needs no `^Xtdb$Connection`: `.connect` resolves off a typed `node` with return type `Xtdb$Connection`, `conn` is tagged from that, and `.submitTx`/`.close` resolve off `conn`.
+
Where you're unsure whether an expression reflects, verify rather than pre-empting.
The dev REPL sets `*warn-on-reflection*` (`src/dev/clojure/user.clj`); the Gradle build does not, so a green test run proves nothing either way.

Use `.getX`, not `.x`, for Kotlin `val` properties::
+
Clojure's `(.x obj)` resolves to a no-arg method `x()` or a public field `x`, and a Kotlin property is neither — it compiles to `getX()` over a private backing field.
So `(.getSchema loader)`, not `(.schema loader)`.

Pass a plain `fn` where a Java functional interface is expected::
+
Clojure 1.12 coerces a `fn` to a `@FunctionalInterface` at an interop site where the compiler knows the target parameter type, so prefer `(.tryAdvance cursor (fn [^RelationReader rel] ...))` over a `reify` of `Consumer` — it drops the boilerplate and the import.
It needs the receiver hinted (`^ResultCursor cursor`) for the overload, and its own param hinted to keep calls against that param out of reflection.

=== Writing tests

(For *running* tests, see <<_testing,Testing>> above.)

Observe real phenomena, not internal calls::
+
Wire up real components - `LiveIndex.open(...)` and the catalogs it needs, `InMemoryLog`, `MemoryStorage` - and assert against observable state: is the data queryable, did the replica log get the right `ResolvedTx`, did the watcher tip into `Failed`.
Lift the expensive ones into `@BeforeEach` fields and close them in `@AfterEach`.
+
Avoid `verify(exactly = N) { mock.someMethod(any()) }`.
Mock-call assertions test *implementation*, not *behaviour* - they pin the test to the current call structure, so a behaviour-preserving refactor (routing the same effect through a different internal API) breaks the test even though the user-visible outcome is unchanged.
Reach for a mock only to inject failure or non-determinism you can't otherwise produce - "what does the leader do when `importTx` throws?" is a legitimate mock; "did `commitTx` get called?" is not.
+
Name tests after the observable behaviour rather than the method on today's code path: `successive external events appear in the replica log with monotonic txIds`, not `subscription routes events through commitTx`.
+
When a refactor surfaces a brittle test, work out what it was protecting and then delete and rewrite it.
Patching tends to keep the bad shape - mock plus verify, name referencing internals - and just shift it sideways.

Don't wrap a single assertion in `t/testing`::
+
Use `t/is`'s message argument - `(t/is <expr> "what this checks")` - which already carries the description into the failure output.
Reserve `t/testing` for grouping *multiple* assertions under a shared context.

Split test namespaces by the surface they exercise::
+
Default to the lowest surface that can express the case, and reach for a higher one only when the case *requires* it - so authz, for instance, defaults to node-level `xt/*` tests in `xtdb.authz-test`, with `xtdb.pgwire.authz-test` taking only the cases that need a real connection (a non-default tx principal, or `pg_catalog` introspection).
The mechanism under test is usually testable without the protocol, and dragging pgwire into every case makes the suite slower and the failures harder to read.

Use dash-free table names::
+
The three table-name representations disagree on kebab-case.
`[:put-docs :my-table …]` normalises the keyword to `my_table`, while the `#xt/table my-table` reader literal and `OpenTx.table(schema, "my-table")` both keep the dash.
A test that writes through one and reads through the other silently addresses two different tables, and the read finds nothing.
Name test tables `:docs`, `:foo` — anything without a dash — and all three agree.

White-box tests of `internal` Kotlin have to be Kotlin::
+
Kotlin `internal` members are JVM name-mangled (`foo$xtdb_core`), so Clojure interop cannot resolve them at all — the failure is `IllegalArgumentException: No matching method`.
A test that needs one has to be a Kotlin test in the same module; the corollary is that tightening a Kotlin member to `internal` breaks every Clojure caller, which is what `xtdb.InternalApi` exists to avoid (see <<_internal_but_public_declarations,Internal-but-public declarations>>).
+
`core/src/test/kotlin/xtdb/indexer/LiveIndexTest.kt` stands up a real `LiveIndex`, catalogs, storage and `OpenTx` without a node — copy its `TestDb` fixture rather than reaching for a full node.
Ingest-and-inspect and on-disk format cases can stay in Clojure at node level (`xt/execute-tx`).

=== Git

We follow https://martinfowler.com/articles/ship-show-ask.html[Ship/Show/Ask] — classify each change by how much pre-merge scrutiny it needs:

Ship::
+
Commit straight to `main`, no PR.
Use for routine, low-risk changes where established patterns apply — small bug fixes, doc tweaks, obvious refactors.
Simple, uncontroversial changes (typos, say, or other non-code changes) can go this way, but be aware of the curse of the 'simple change' — err on the side of caution if need be.

Show::
+
Open a PR, then merge it promptly yourself.
The PR exists for async visibility and post-hoc feedback, *not* as a review gate.
Use when you're confident in the change but want it seen — new approaches, non-trivial refactors, anything worth a teammate noticing.

Ask::
+
Open a PR and wait for input before merging.
Use when the change is uncertain, experimental, or invites discussion — you're genuinely asking, not informing.

The key distinction between show and ask: show merges without waiting; ask waits.
Default toward show over ask when you're confident — don't manufacture review gates for changes you'd stand behind anyway.

For show and ask changes, run a code-review pass over the diff before raising the commit or PR — the `/code-review` skill, or a code-review agent (e.g. `feature-dev:code-reviewer`).
Ship changes don't need it.
Whether the findings block the commit/PR or are merely noted is a judgement call on their severity and the cost to address: fix what's cheap and clearly right, and raise the rest rather than sitting on it.
Since show and ask normally go through plan mode, this review MUST appear as an explicit step in the plan, ahead of the commit/PR step (alongside the chalk and chill steps).

NOTE: AI agents working in this repo — if you're not sure which path applies, ask the human you're paired with rather than guessing.
